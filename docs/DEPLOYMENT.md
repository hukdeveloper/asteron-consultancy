# Deployment Guide — Janan Consultancy (Phase 8, hosting comparison added Phase 9, static export added Phase 10B "Phase C")

Platform-neutral. This document describes what any hosting platform needs to provide and what to configure — it does not assume Vercel, Netlify, Hostinger, or any other specific provider. Pick a platform; nothing here should need to change as a result.

## 1. What this application is

A Next.js 16 application built as a **static export** (`output: "export"` in `next.config.ts` — see docs/DECISIONS.md C-069). Every route was already static/SSG with no API routes or request-time server logic (see [docs/ROUTE_INVENTORY.md](ROUTE_INVENTORY.md)), so `next build` now produces a plain `out/` directory of HTML/CSS/JS — no Node runtime is required to serve it. It can be uploaded to **any** static file host (Hostinger shared hosting, S3, GitHub Pages, Netlify, Cloudflare Pages, a plain nginx/Apache box) exactly as-is, and still works unchanged on Vercel.

Two things a plain static host can't do that a Node server previously did, both handled outside `next.config.ts` now instead:

- **Security headers** — no longer set by `next.config.ts`'s `headers()` (unsupported in export mode). The Apache/`.htaccess`-based hosts (Hostinger shared hosting included) get them from `public/.htaccess`, which is copied into `out/.htaccess` on every build — see §6. A host that doesn't read `.htaccess` (S3, GitHub Pages, a raw CDN) needs the equivalent configured at that host/CDN layer instead.
- **Clean, extensionless URLs** (`/about` instead of `/about.html`) — `next build` emits `about.html`, not `about/index.html` (`trailingSlash` is left at its default `false` deliberately — see docs/DECISIONS.md C-069 for why). `public/.htaccess` includes a `mod_rewrite` rule that resolves `/about` → `about.html` on Apache. A host without `.htaccess` support needs its own equivalent rewrite/redirect rule, or accept `.html`-suffixed URLs.

`src/app/sitemap.ts`, `src/app/robots.ts`, `src/app/icon.tsx`, and `src/app/opengraph-image.tsx` all carry `export const dynamic = "force-static"` (required for export mode — see docs/DECISIONS.md C-069) and are generated once at build time into the `out/` directory.

## 2. Build and serve commands

```
npm ci
npm run build
npm run start
```

`npm run build` runs `next build`, which also runs a full TypeScript check (fails the build on any type error — do not skip this by using a "build" script that bypasses it), and writes the deployable site to `out/`. `npm run start` now runs `serve out -p 3000` (a plain static file server — `next start` errors outright with `output: "export"`, and Next itself tells you to use this instead) — this is for local preview/testing of the exact production output, not something you'd typically run on the actual host; the real host just needs to serve the `out/` directory's contents directly (e.g. Hostinger's File Manager/FTP upload, or any static-hosting platform's deploy step).

## 3. Environment variables

See `.env.example` for the complete, current list — there is exactly one:

| Variable               | Required                | Purpose                                                                                                                                                                                                                                                                                                                        |
| ---------------------- | ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `NEXT_PUBLIC_SITE_URL` | **Yes, for production** | Absolute site URL used for `metadataBase`, canonical links, Open Graph URLs, and `src/app/sitemap.ts`/`robots.ts`. Falls back to `http://localhost:3000` if unset (`src/lib/env.ts`) — the site will build and run without it, but every canonical/OG/sitemap URL will be wrong, which is a launch blocker, not a build error. |

No secrets, API keys, or database connection strings exist because there is no external service or database in this track.

## 4. Node.js version

No `engines` field is currently pinned in `package.json`. This project was developed and tested against a current Node.js LTS release (Node 24 in this environment). Recommend pinning `engines.node` to whatever LTS the chosen platform runs once a platform is selected, and matching CI to the same version — an unpinned engine is a minor, easy-to-fix gap, not a blocker.

## 5. Static assets and caching

- `public/images/`, `public/videos/`, and Next.js's own `_next/static/*` output should be served with long-lived, immutable cache headers (Next.js's default build output is already content-hashed, so this is safe) — most platforms with native Next.js support configure this automatically; confirm it if self-hosting behind a custom reverse proxy.
- No CDN-specific configuration exists or is required by the application itself; any CDN in front of it should respect the cache headers Next.js already sets rather than overriding them with a shorter TTL.
- `next/image` optimization (used nowhere yet, since no photography exists — see docs/MEDIA_ATTRIBUTIONS.md) will need either the platform's built-in image optimizer or a configured custom loader once real photography is added.

## 6. Security headers

Since the switch to static export (docs/DECISIONS.md C-069), these are configured in **`public/.htaccess`** (copied to `out/.htaccess` on every build), not `next.config.ts`: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, a restrictive `Permissions-Policy`, and `Strict-Transport-Security` (only takes effect once served over HTTPS — safe to send in the meantime, browsers ignore it over plain HTTP).

This works automatically on any Apache-based host (Hostinger shared hosting included) — nothing to configure beyond uploading `out/.htaccess` along with everything else in `out/`. A host that doesn't honor `.htaccess` (S3, GitHub Pages, Cloudflare Pages, a raw CDN, Vercel) needs the same five headers configured at that platform's own header-configuration layer instead (e.g. a `_headers` file for Netlify/Cloudflare Pages, `vercel.json` `headers` for Vercel) — `.htaccess` itself is inert there.

**Content-Security-Policy is deliberately not set** (see the doc comment in `next.config.ts` and docs/DECISIONS.md). A meaningful CSP for this app needs per-request nonces generated in Next.js 16's `proxy.ts` (the successor to middleware) plus every inline script/style wired to that nonce, and pages using them opted into dynamic rendering — none of which exists yet. Shipping a static CSP today would either break the app (if strict) or provide no real protection (if permissive enough not to break it). **This is a genuine, tracked launch consideration, not an oversight:** implement the nonce/proxy architecture and a real CSP before launch if CSP is required by policy, or explicitly accept its absence as a launch decision — either way, do not add a placeholder CSP header that merely appears present without functioning.

## 7. Forms — what must exist before any form is connected

All four forms (`/book-consultation`, `/check-eligibility`, `/insurance-quote`, `/contact`) are currently client-side-only demos — no request leaves the browser (see docs/TECHNICAL_ARCHITECTURE.md §5). Before pointing any form's `SubmissionAdapter` at a real service (Track 2), the destination must independently provide or this application must add: server-side validation mirroring each Zod schema, rate limiting, bot protection (honeypot and/or timing heuristic; CAPTCHA only if abuse is actually observed), CSRF protection appropriate to the chosen transport, spam filtering, request-size limits, TLS-only transport, data minimization, a documented retention period, access controls, an audit trail, and redaction of personal fields from logs. None of this is deployment configuration for the _current_ static site — it is a prerequisite for the _next_ track, recorded here so it isn't forgotten when that track begins.

## 8. Cookies and analytics

No analytics, advertising, or consent-management cookies are set by this application today (verified in `src/content/legal.ts`'s Cookie Policy content and by inspection — no analytics script exists anywhere in the codebase). **No cookie consent banner is needed at launch.** If a future phase adds analytics, the Cookie Policy and this section must be updated together, and a consent mechanism added before any non-essential cookie is set.

## 9. Custom domain and DNS

Standard for any static/SSR Next.js host: point the domain at the platform per its own instructions, provision a TLS certificate (most platforms automate this), and set `NEXT_PUBLIC_SITE_URL` to the final `https://` domain before the production build that will actually be deployed — canonical URLs and the sitemap are baked in at build time, not computed per-request.

## 10. Redirects and legacy URLs

None exist or are needed — this is a new site with no prior URL structure to preserve.

## 11. Monitoring, logging, and error tracking

Not implemented in this track (no error-tracking SDK, no structured logging, no uptime monitoring) — deliberately deferred per docs/DECISIONS.md (C-010, "deferred structured-logging scaffold"). The custom `error.tsx`/`global-error.tsx` boundaries and `not-found.tsx` page handle client-visible error states; nothing reports these anywhere today. Add basic uptime monitoring and, if desired, a client error-reporting service, as a pre-launch or post-launch decision — neither blocks a launch on its own, but launching with zero visibility into runtime errors is worth an explicit decision rather than a silent gap.

## 12. Rollback strategy

Standard for any static/SSR deployment: keep the previous build's deployment artifact available (most platforms do this automatically via deployment history) and roll back to it if a new deployment introduces a regression. No database migrations exist in this track, so a rollback is always safe and reversible — there is no persisted state to reconcile.

## 13. Health checks

No dedicated health-check endpoint exists. Any platform-level health check can simply request `/` (or `/robots.txt`, which is lighter) and expect a 200.

## 14. Backups

Not applicable in this track — there is no database and no persisted user data. The only durable state is the Git repository itself.

## 15. Post-deploy verification checklist

After any production deployment:

- [ ] `/sitemap.xml` and `/robots.txt` resolve and reference the correct production domain (not `localhost`).
- [ ] `/opengraph-image` and `/icon` render correctly (share a link to the homepage on a platform that shows link previews).
- [ ] All four forms show the not-connected message on a valid submission, and no network request is visible in the browser's dev tools network tab.
- [ ] Security headers are present (`curl -I https://<domain>/` and check for `X-Frame-Options`, `Strict-Transport-Security`, etc.).
- [ ] HTTPS is enforced (HTTP requests redirect to HTTPS).
- [ ] Every item under "Blockers" in [docs/PRODUCTION_CONTENT_CHECKLIST.md](PRODUCTION_CONTENT_CHECKLIST.md) has been resolved — this is a content/business decision, not a technical deployment step, and remains the responsibility of the lead architect to confirm before announcing the site as live.

## 18. Static hosting — Hostinger (or any Apache/`.htaccess`-based shared host)

1. Set `NEXT_PUBLIC_SITE_URL` to the real production domain (e.g. `https://jananconsultants.com`) in the environment the build runs in — canonical URLs, Open Graph URLs, and the sitemap are baked in at build time, not computed per-request, so this must be correct **before** running the build that gets uploaded, not fixed after.
2. `npm ci && npm run build` — produces the complete site in `out/`, including `out/.htaccess` (security headers + clean-URL rewrite rule, copied from `public/.htaccess`).
3. Upload the **contents** of `out/` (not the `out/` folder itself) to Hostinger's `public_html/` (or the docroot for the target domain/subdomain) — via hPanel's File Manager (zip `out/`'s contents, upload, extract in place) or FTP/SFTP. Confirm `.htaccess` made it across — some FTP clients hide dotfiles by default.
4. Confirm HTTPS is enabled for the domain (Hostinger provisions a free Let's Encrypt certificate per domain in hPanel) — `Strict-Transport-Security` from `.htaccess` only has any effect once the site is actually served over HTTPS.
5. Run the §15 post-deploy verification checklist against the live domain.

Re-deploying an update is the same three steps: rebuild locally (`npm run build`), re-upload `out/`'s contents (overwriting what's there), re-run §15.
